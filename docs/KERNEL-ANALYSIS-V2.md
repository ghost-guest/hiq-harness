# 内核方案 V2：从需求反推，按第一原理重判

> 本文修正 V1 中对 `dim` 的过粗判定，并把评判标准从「谁的架构好看」
> 换成「谁满足本项目的硬契约」。
> 证据：`ghost-guest` 670 个 star 全量 + 18 个仓库源码。

---

## 0. 先认错：V1 在 dim 上判粗了

V1 只写了「rutis 绑定 + 388k 行 + alpha → 参考」，没回答一个关键问题：
**它被夸的到底是什么？**

答案：被夸的是**设计**，而且设计确实是全场最好的。dim 的 time-bus 六条原则
（只认总线序号 / 状态是事件折叠 / 副作用不重放 / 每份状态单所有者 / 原子批 / 可回放）
与本项目 L0「日志是事实，其余都是投影」是**近同构**——这不是巧合，是同一个第一原理推导出的同一个结果。

但「设计对」和「能当稳定内核」是两件事。下面用需求把这两件事分开。

---

## 1. 从现有项目反推：内核必须满足的 14 条硬契约

出处：`IMPLEMENTATION.md` 第 4 节 + `AGENTS.md` 「七个机制的核心纪律」+ `README.md`。

| # | 契约 | 出处 | 违反的后果 |
|---|---|---|---|
| R1 | 消息是日志的纯函数；append-only + seq | kiso 三契约 | 状态与历史分叉，重放不可信 |
| R2 | 裁决持久化：`kill -9` 后已决定的不重问 | kiso | 恢复后重复询问/重复执行 |
| R3 | 副作用留收据；`uncertain` 必须阻塞 | kiso | 静默重试造成重复副作用 |
| R4 | 不设硬步数上限，终止靠守卫 | Codewhale | 合法长任务被杀 |
| R5 | 守卫只对「相同失败」熔断；指纹含 blocks | maka / Raven | 误杀轮询与迭代重试 |
| R6 | 压缩只改投影；缓存前缀冻结；miss 可归因 | opencode / Codewhale | 缓存命中归零，成本暴涨 |
| R7 | 记忆项目内、准入不可反序列化、配额只降不升 | ownmem / Codewhale | 记忆越权/审计断链 |
| R8 | 恢复要租约 + 代次围栏；记忆失效拒绝交出 state | LoopForge / Codewhale | 旧实例复活写乱 |
| R9 | SOP DAG + human gate + 前置能力声明 | LoopForge | 流程中途失败 |
| R10 | 项目扩展不能覆盖内建；坏插件启动即失败；策略链单调 | kiso | clone 下来的仓库改掉 CLI 行为 |
| R11 | 桌面/手机/编辑器走同一协议，无伪造 method | 本项目 `docs/orbit-harness.md` | 每个客户端一套适配 |
| R12 | 长会话稳态缓存命中 >90% | 本项目 `docs/CACHE-BENCHMARK.md` | 成本不可接受 |
| **R13** | **Go 插件层（用户明确要求）** | 你 | 扩展只能改内核源码 |
| **R14** | **内核小且稳定，能力通过插件实现（用户明确要求）** | 你 | 内核随功能膨胀，改不动 |

**R13 + R14 不是修饰，是架构分界线。** 它们等价于一条第一原理：

> **内核只持有「不可外置的确定性」，其余一切都必须是进程外的能力。**

## 2. 第一原理：内核到底不可再分的是什么

把 14 条契约做最小闭包，内核只该有 6 个职责、5 个接缝。

### 6 个职责（必须在核内，否则契约不成立）

| 职责 | 为什么不能外置 | 对应契约 |
|---|---|---|
| ① 事件日志（append-only + seq + 组提交） | 外置则「真相」多份，R1/R2 破 | R1 R2 |
| ② 投影（state = fold(log)） | 投影若由插件算，插件崩溃=状态不可信 | R1 |
| ③ Turn 状态机 + 守卫 | 终止策略外置 = 插件可以永不退出 | R4 R5 |
| ④ 收据账本 + uncertain 阻塞 | 这是「副作用是否发生过」的唯一权威 | R3 R8 |
| ⑤ 策略链 + 审批裁决 | 单调性必须在核内（deny>allow>ask） | R10 |
| ⑥ 上下文视图（压缩/裁剪） | 压缩改的是喂给模型的投影，必须可归因 | R6 R12 |

### 5 个接缝（必须有 schema + 版本号）

| 接缝 | 方向 | 协议 | 稳定性要求 |
|---|---|---|---|
| S-A 客户端协议 | 桌面/手机/编辑器 → 内核 | JSON-RPC（无 `jsonrpc` 字段）+ 通知流 | 版本协商，加法演进 |
| S-B 插件协议 | 内核 ↔ Go 子进程 | JSON-RPC over stdio，一插件一进程 | 坏插件启动即失败；崩溃隔离 |
| S-C 模型传输 | 内核 → provider | trait（已有 aimux 实现） | 不锁厂商 |
| S-D 审批回调 | 内核 → 客户端 | 反向 request | 必须应答，超时=拒绝 |
| S-E 存储 | 内核 → 磁盘 | 日志/检查点/记忆三段 | 可重放校验 |

**这条推论的杀伤力**：任何把「工具实现、集成、UI、厂商逻辑」塞进内核的仓库，
都天然违反 R14——不管它多强。

## 3. dim 的辩证评估（逐条举证）

### 它真强的地方（X 上夸的是这些）

| 强项 | 证据 | 与本项目的关系 |
|---|---|---|
| 时间线只认序号，执行快慢不影响语义 | `docs/architecture/rust-agent/time-bus.md` §1 | 正是 R1 想要的 |
| 状态 = 事件折叠，可回放 | 同上 §3 | 正是 R1 |
| 副作用不重放，总线只记结果 | 同上 §5 | 正是 R3 |
| 每份状态单所有者 | 同上 §2 | 正是 R8 的前提 |
| 原子批 + 按序派发 | `principles.md:67` | 组提交的同构 |
| 协议有真版本协商（v4 + feature gate） | `dim-app-server/src/protocol.rs:8` | R11 想要的样子 |
| 压缩策略可插拔、有保留窗口 | `context_policy.rs:82-97` | R6 |

**这些加起来，说明 dim 的内核语义是本项目 L0 的最佳参考实现。**

### 它不能当「稳定内核」的地方（这是判定的真正理由）

| 问题 | 证据 | 破坏哪条 |
|---|---|---|
| **alpha 未发布**：`0.1.0-alpha.25`，`git tag` 为 0 | `Cargo.toml:8` | R14（稳定） |
| **运行时地基是第三方 0.x 框架**：`rutis 0.19.3`，文档记录 0.15→0.16→0.19 三次破坏性升级 | `Cargo.toml:17-19`；`docs/INDEX.md:97-99` | R14 |
| **插件不是 Go**：rutis 只给 Rust/TS 绑定 | `docs/typescript-plugin-authoring.md:3` | **R13 直接不成立** |
| **UI 真相源另走广播**，不是时间线 | `principles.md:84` | R1 打折（两份真相） |
| **sandbox 默认关闭**（opt-in） | `docs/adr/010-sandbox-opt-in.md` | R10 |
| 体量 38.9 万行（其中内核三件 81,780 行）、113 个 RPC 方法 | 实测 `crates/*/src`、`dim-agent-{capabilities,types}`+`dim-event-hub` | R14 |
| 无 rewind，只能 fork | `docs/design/timeline-branches.md:57` | 不影响契约，但体验差 |

**辩证结论一句话：**
> dim 的**语义**是本项目最该抄的；dim 的**交付形态**（alpha + rutis + Rust/TS 插件）恰好同时违反 R13 和 R14。
> 所以正确动作不是 fork 它，而是**把它的 time-bus 六条写成内核的 L0 规格，然后自己实现 1 万行**。

## 5. 稳定性论证：什么才算「内核稳定」

「稳定」不是「没 bug」，是可操作的三件事：

| 判据 | 含义 | 怎么验 |
|---|---|---|
| **S1 接口面小** | 对外 5 个接缝，每个有 schema + 版本 | 数 method，数 schema 文件 |
| **S2 地基不漂移** | 不把运行时建在 0.x/自研框架上 | 查 Cargo.toml 里 0.x 依赖 |
| **S3 可重放** | 任何状态都能从日志重建，CI 有 replay 测试 | 跑 replay 测试 |
| **S4 策略在核内** | 插件不能削弱策略；插件崩溃不影响内核 | 断插件进程看内核是否活 |
| **S5 依赖单向** | 内核不依赖 UI/产品层 | 查依赖图 |
| **S6 发布可控** | 有 semver tag，能钉版本 | `git tag` |

对照：

| 项目 | S1 | S2 | S3 | S4 | S5 | S6 |
|---|---|---|---|---|---|---|
| dim | △(113) | ✗(rutis 0.19.3) | ✓ | △ | △ | ✗(0 tag) |
| codewhale | △(40+274+ACP) | ✗(codegen 锁 codex v0.166.0) | ✓ | ✓ | ✓ | ✓(v0.10.3) |
| codex | ✓ | ✗(OpenAI 后端/账号) | ✓ | ✓ | ✓ | ✓ |
| prime-agent | ✓(8 ACP) | ✓ | ✓ | ✗(无审批/沙箱) | ✓ | △ |
| PiG | ✗(无协议) | ✓ | ✓ | △ | ✓ | ✗(0.x) |
| goose | △ | ✓ | △ | ✗(无 sandbox) | ✗(195k 产品) | ✓ |

**S2 和 S6 是「稳定」的硬指标，dim 两条都不满足。**
X 上夸它的那批人看的是 S3/S4 的**语义质量**，不是交付稳定性。

## 6. 最终架构：microkernel + Go 插件

### 分层（依赖单向，箭头不可逆）

```
客户端（GPUI 桌面 / 手机 / 编辑器）
        │  S-A 客户端协议（JSON-RPC + 通知流）
        ▼
┌─────────────────────────────────────────────┐
│  内核 harness-kernel（Rust，目标 8–15k 行）  │
│                                             │
│  log ─ projection ─ turn machine ─ guards   │
│  receipts ─ policy ─ context view           │
│                                             │
│  5 接缝：S-A 客户端 / S-B 插件 / S-C 模型 /  │
│          S-D 审批 / S-E 存储                 │
└─────────────────────────────────────────────┘
        │ S-B（JSON-RPC over stdio，一插件一进程）
        ▼
Go 插件（tools / hooks / approvals / integrations）
```

### 内核模块清单（每个都有唯一来源）

| 模块 | 职责 | 规格来源 |
|---|---|---|
| `log` | append-only + seq + 组提交 | pi `group-commit.md`；dim `time-bus.md` §1 |
| `projection` | fold(log) → messages | dim `time-bus.md` §3 |
| `turn` | 单 turn 状态机 + 流式 | pi `packages/agent/src/agent-loop.ts:184-313` |
| `steer` | 安全点注入 | jcode `turn_streaming_mpsc.rs:1431-1450` |
| `guards` | 三件套（失败熔断/阶梯/只读螺旋） | maka / Raven / 天枢（现有实现可直接搬） |
| `receipts` | 收据 + uncertain 阻塞 | kiso `durability.md` |
| `policy` | deny>allow>ask 单调链 | kiso `extensions.md` |
| `context` | 压缩视图 + 缓存守卫 | opencode 常量 + openhuman `PromptCacheGuardMiddleware` |
| `seam/clients` | JSON-RPC 无 `jsonrpc` 字段 | codex `app-server-protocol/src/rpc.rs:1-2` |
| `seam/plugins` | 一进程一插件 + 版本握手 | 自定（见下） |
| `seam/model` | trait + aimux 实现 | 已有 |
| `store` | 日志/检查点/记忆 | 现有 L5 设计 |

### S-B 插件协议（这是 R13 的落地点，必须先定死）

```
内核 → 插件：  {"id":1,"method":"plugin/hello","params":{"protocol":1,"caps":[...]}}
插件 → 内核：  {"id":1,"result":{"name":"git","protocol":1,"tools":[...],"hooks":[...]}}
内核 → 插件：  {"id":2,"method":"tools/call","params":{"tool":"git.status","input":{...}}}
插件 → 内核：  {"id":2,"result":{"content":"...","is_error":false}}
内核 → 插件：  {"method":"hooks/pre_tool","params":{...}}   # 通知，无应答
```

规则（每条对应一条契约）：
1. `plugin/hello` 不带 `protocol` 或版本不匹配 → **启动即失败**（R10）
2. 插件声明的 `caps` 由内核复核，项目级插件不能放宽内建策略（R10）
3. 插件进程崩溃 → 内核标记该插件不可用，**内核不崩**（R14 S4）
4. 工具调用返回 `uncertain` → 收据记 `Uncertain` 并阻塞（R3）
5. 插件不得直接写日志/状态；只能通过返回值（R1）

### 为什么这个架构「稳定」

- 内核 5 个接缝全部版本化 → 插件/客户端可以独立演进（S1）
- 内核不依赖任何 0.x 框架；不依赖厂商后端（S2）
- 日志重放测试是 CI 第一道门（S3）
- 策略链在核内，插件只能提议不能裁决（S4）
- 内核不依赖 UI；UI 只是 S-A 的消费者（S5）
- 打 semver tag，插件协议带版本号（S6）

## 7. 我可能错的地方（反方举证）

诚实地列出三个「我可能判断错」的点：

1. **「自建 1 万行」可能低估。** 对比：pigo 的 loop 只有 192 行，但完整的 steer+并行+子 agent+压缩 是 7.6 万行。
   1 万行只覆盖「骨架 + 2 个守卫 + 协议」，不含沙箱与记忆。真实目标应是 **1.5–2.5 万行**，工期 6–8 周。
2. **dim 的 alpha 不代表不可用。** 它每天有提交、有 113 个 method 的协议、有 ADR 文档体系。
   如果只看「能不能跑起来」，它比很多 1.0 项目更完整。我的反对理由是 S2/S6（可钉版本、地基不漂移），
   不是「它不好」。如果你能接受每两周跟一次 rutis 升级，fork dim 也成立——但它仍不满足 R13（Go 插件）。
3. **codewhale 可能被低估。** 它是唯一「MIT + sandbox + execpolicy + 协议兼容 codex + MCP stdio」齐全的仓库。
   如果 R14 放宽（接受 55 万行、接受跟上游 schema），它是最快能出成品的路径。

## 8. 结论

1. **底座选「自建 microkernel」**，目标 1.5–2.5 万行，6–8 周。
2. **L0 语义直接采用 dim 的 time-bus 六条**（这是它真正的价值，也是你看到 X 上那批好评的原因）。
3. **协议形状抄 codex，协议版本法抄 codewhale，ACP 接入抄 goose，steer 抄 pi/jcode。**
4. **Go 插件协议按第 6 节先定死再写内核**——它不是「后续的事」，它是 R13/R14 的分界线。
5. dim 不作为底座，但它的 `time-bus.md` 与 `context_policy.rs` 是必读规格。

### 下一步三件事（等你确认）

1. 内核目标体量：**1.5–2.5 万行 / 6–8 周** 是否可接受（对应第 7 节第 1 条的自查）
2. S-B 插件协议要不要我直接写成 `docs/PLUGIN-PROTOCOL.md`（含 5 条规则的测试用例）
3. 要不要把 dim 的 `time-bus.md` 六条翻译成内核的 L0 验收标准（每条一个可跑的 replay 测试）
